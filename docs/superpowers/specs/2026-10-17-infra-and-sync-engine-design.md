# awsome-ella 重设计 — 子项目 1：基础设施与同步引擎

日期：2026-10-17
状态：已评审通过（2026-10-17 三处待确认项已由用户裁定），待写实现计划
覆盖范围：仅子项目 1（认证、本地存储、同步引擎、迁移通道、表约定）。业务模块的数据模型不在本 spec 内。

## 1. 背景与目标

现有 `index.html` 是 1108 行单文件应用：纯 vanilla JS，把状态整体 JSON 序列化进单个 localStorage key
`wb_tw_data`，模块渲染靠 `innerHTML` 字符串拼接。已确认的具体问题：

- 导出/导入 key 清单不一致，恢复时丢失 `exams`（学情分析数据）
- 座位缩放按钮事件名与处理器不匹配，功能失效
- localStorage 写满时仅弹提示，内存中的编辑实际未持久化
- 图片以 base64 存入同一条记录，是配额压力的主因
- 无 schema 版本号，无法迁移
- 及格线计算按 100 分制硬编码，与分科满分口径冲突

重设计目标：转为前后端分离、云端存储、**本地优先且可联网同步**的应用。

## 2. 决策记录

| 决定 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 运行形态 | 前后端分离 + 数据库 | 用户选定；需要云端留存与多设备 | 继续单文件 localStorage |
| 后端 | 复用用户已有的 Supabase 实例 | 接入最快、免运维；数据驻留由用户自有实例决定 | Qoder Sites 托管；自建 Node+Postgres |
| 离线能力 | 本地优先 + 后台同步 | 教室网络不稳定，离线录入必须可用 | 纯在线（会失去现应用的离线性质） |
| 冲突解决 | 逐行 LWW + 软删除墓碑 | 单一作者，无需协同编辑 | CRDT（复杂度与场景不匹配） |
| 用户与权限 | 单教师，RLS 强制 `owner_id` | 用户选定；隔离在数据库层成立而非靠前端隐藏 | 学生/家长只读角色（延后） |

### 2.1 数据驻留与信息最小化

后端为**用户自有的 Supabase 实例**，数据不出现在任何第三方托管环境，不存在数据出境问题。
在此基础上仍保留信息最小化设计，理由是降低泄露影响面而非合规妥协：

- 数据库不设计身份证号列
- 家长电话等为独立可空列，可批量导入（见 §6），不强制采集
- 相册放入私有 bucket，不使用公共 URL
- 连接串、密钥、bucket 名全部来自环境变量，换实例时只改配置不改代码

## 3. 架构

```
UI (Vue 3 组件)
  │  读：仅读本地
  │  写：落本地 → 入 outbox → 返回成功
  ▼
LocalStore (IndexedDB / Dexie)
  ├── 业务表镜像（与远端同名同主键）
  ├── outbox：待推送操作队列
  └── sync_meta：水位线、device_id、同步状态
  ▲
  │  push（按序）/ pull（realtime + 水位线补拉）
  ▼
Supabase  (PostgREST + Auth + Storage + Realtime)
```

技术选型：Vite + TypeScript + Vue 3（模板渲染替掉 `innerHTML` 拼接，消除转义遗漏类缺陷）；
Dexie 封装 IndexedDB；`@supabase/supabase-js` v2。

边界与职责：

- **LocalStore**：唯一的数据读源。不知道网络是否存在。
- **SyncEngine**：唯一能写远端的组件。不暴露给业务模块，业务只调 LocalStore。
- **Repository**（每模块一个）：把业务语义翻译成表操作。业务组件不直接接触 Dexie 或 Supabase。

判定标准：业务模块要读写数据，只可能通过 Repository；要新增一张表，只需声明 schema + 注册进同步清单，
不必再写一遍同步代码。

## 4. 统一表约定

每张业务表（本地与远端同构）必须包含：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 客户端生成，离线可创建 |
| `owner_id` | uuid | 当前教师 auth uid，RLS 依据 |
| `seq` | bigint | 本地单调序号，时钟无关的决胜依据 |
| `updated_at` | timestamptz | **服务端时间戳**，不由客户端提供 |
| `deleted_at` | timestamptz null | 软删除墓碑 |
| `device_id` | text | 写入来源设备，配合 `seq` 决胜 |

删除一律软删除：硬删除时拉取端无法得知该行应被移除，会在其他设备上复活。

所有建表脚本置于 `supabase/migrations/*.sql`，按文件名顺序编号，解决现状无版本化的问题。
RLS 策略统一为 `owner_id = auth.uid()`，select/insert/update/delete 四条都要开。

## 5. 同步设计

### 5.1 写路径

1. 业务调 Repository 写方法
2. 同一 Dexie 事务内：写业务表 + 追加 outbox 条目（含 `op`/`table`/`id`/`payload`/`seq`）
3. 立即返回，UI 更新
4. SyncEngine 被唤醒执行 push

「已保存」= 第 3 步完成。「已同步」= 第 4 步服务端确认。UI 必须分开显示这两态，并显示待同步条数。
不合并成一个提示——这是现有应用把配额失败伪装成成功的同类错误。

### 5.2 push

按 `seq` 升序取 outbox 条目，分批 upsert。`updated_at` 由数据库的 `before insert or update` 触发器
统一赋 `now()`，客户端 payload 中不含该列（因此不能依赖 PostgREST 自动填充，必须显式建触发器）。
成功则删除对应 outbox 条目；失败则保留队列、指数退避重试，不丢数据。

### 5.3 pull

在线时订阅 Supabase realtime 变更事件；每次恢复连接、应用启动、窗口重新获得焦点时，
按 `updated_at > 水位线` 补拉一次，修正订阅期间漏掉的事件。补拉后推进水位线。

### 5.4 冲突决胜

只在同一教师的多个设备间发生（**已确认为单作者场景**，若将来出现两人同班操作需重评此节）。规则：

1. 以服务端 `updated_at` 做 LWW；
2. `updated_at` 相等（同批写入）时，比较 `seq`，大者胜；
3. `seq` 也相等则比 `device_id`，保证确定性、避免抖动。

明确不使用客户端挂钟：设备时钟偏差会让旧编辑覆盖新编辑，这是 LWW 的经典失效模式，
故 `updated_at` 一律由服务端生成。

### 5.5 图片

新增图片：原图先写入 IndexedDB blob store 并立即渲染，同时把上传任务入 outbox，联网后传 Storage，
成功后远端行只存 object path，**不存 base64、不存字节**。查看一律读本地。
效果：离线可拍可看，且数据库不再承载二进制，配额压力从 localStorage 的约 5MB 转到 IndexedDB 的
百 MB 量级。

## 6. 旧数据迁移

一次性入口，读 `wb_tw_data` JSON，按字段映射写入 LocalStore，随后由正常同步推送。

- 映射清单由 schema 定义生成，而非手写数组——这从结构上避免复现「漏 `exams`」缺陷
- 迁移前做完整 JSON 导出备份并保留
- 旧字段 `parentName`/`parentPhone` 映射到新列，联系方式等个人信息**随常规批量导入一并写入，不额外设卡**；
  同时支持从 CSV/XLSX 批量导入联系方式（沿用现应用已有的表格解析能力，迁移到 Repository 层）
- 导入时校验行级格式（电话位数/邮箱形状），失败行汇总报告而非静默跳过或整批中断
- 迁移幂等：按 `id` upsert，重复执行不产生副本

## 7. 错误处理

| 情况 | 行为 |
|---|---|
| 离线 | 正常写入，UI 标「待同步 N 条」，不报错 |
| 推送失败（网络/5xx） | 条目留队，指数退避重试 |
| 推送被 RLS 拒绝（403） | 视为程序缺陷，停止该条目重试并显式报错，不静默丢弃 |
| IndexedDB 不可用（无痕模式等） | 启动即检测并说明限制，降级为纯内存会话，明确告知数据不持久 |
| 认证过期 | 保留本地数据与队列，跳登录，重登后继续同步 |
| 存储配额逼近 | 主动提示清理相册原图，而非等到写失败才弹 toast |

## 8. 测试策略

- **单元测试**：冲突决胜矩阵（`updated_at`/`seq`/`device_id` 各种相等与大小组合）、软删除复活场景、
  水位线推进、outbox 顺序与重试退避
- **集成测试**：FakeIndexedDB 跑「离线写 N 条 → 恢复网络 → 全部正确落库且顺序不乱」；
  「双设备并发编辑同一行」验证 LWW 结果确定
- **迁移测试**：以现有 `wb_tw_data` 真实结构样本做输入，断言映射后各表行数与旧 JSON 逐项一致
- 本 spec 不含业务模块，故不做端到端业务测试；那属于子项目 2-4

## 9. 验收标准

1. 全程断网操作 30 次写入，恢复网络后远端 30 条齐全、顺序与本地一致、无重复
2. 两个浏览器实例编辑同一行，刷新后两端收敛到同一结果且可解释
3. 删除一行后在另一设备刷新，该行不复活
4. 相册在断网时可新增并可查看
5. 旧数据导入后逐项比对无字段丢失（含 `exams`）
6. 新增一张业务表时，仅需 schema + 同步清单注册，不新增同步代码

## 10. 非目标

- 学生/家长登录与只读视图（子项目后续）
- 多班级、多租户
- 具体业务界面与模块行为重设计（子项目 2-4）
- 现网 `index.html` 的行为改动：本 spec 期间不动它，作为参考与迁移数据源保留
